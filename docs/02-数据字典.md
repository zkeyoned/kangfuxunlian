# 02 · 数据字典

> 权威定义在 `database/schema.sql`（带注释）。这里是给非后端同学看的人话版。
> 原则：**只存关键点推导出的指标，不存视频、不存原始关键点。**

## 一张图看关系

```
institutions（机构）
   └── users（账号：admin / therapist / patient）
          └── patients（患者档案，1:1 患者账号）
                 ├── consents（知情同意，版本化）
                 ├── plans（训练计划）
                 │      └── plan_items（计划里的每个动作：组数/次数/目标角/规则版本）
                 ├── sessions（一次训练）
                 │      └── session_items（一组动作的结果）
                 │             ├── reps（每一次动作）
                 │             └── session_events（逐条提示事件，20260919 新增）
                 └── alerts（给康复师的提醒）

exercises（动作字典）──▶ rule_versions（动作规则，版本化，双人审核）
audit_logs（审计：谁在什么时候动了什么）
tokens（登录会话）
```

## 表说明

增量关联功能（待数据库负责人审核）：`backend/migrations/001_care_requests.sql` 创建 `care_requests`，存 sender_id / recipient_id / patient_id / therapist_id、pending/accepted/rejected/cancelled 状态及创建/更新时间。待处理的 patient_id + therapist_id 组合唯一。现有14表不变，已接受的当前主责关系仍以 patients.therapist_id 为准。解除后保留申请审计与历史，患者 active 计划暂停。

权限补充：普通康复师按 patients.therapist_id 查看已关联患者，不再按机构查看所有患者；admin 仍按 institution_id 限定。关联不迁移患者机构。审计新增 care.request / care.accept / care.reject / care.cancel / care.unlink。

| 表 | 一行是什么 | 关键字段 | 谁写入 |
|---|---|---|---|
| `institutions` | 一家机构 | name | 管理员 |
| `users` | 一个账号 | role, username, password_hash（pbkdf2-sha256） | 管理员/康复师建患者 |
| `tokens` | 一次登录 | token, expires_at（72h） | 登录接口 |
| `patients` | 患者档案 | surgery_type, surgery_date, affected_side(L/R), phase, baseline_json | 康复师 |
| `consents` | 一次知情同意 | version, text_sha256, agreed_at, withdrawn_at | 患者首次登录/撤回 |
| `exercises` | 一种动作 | code(候选：SLR/KNEE_FLEX/SQUAT/STS/SEATED_KNEE_EXTENSION，以康复师确认结果为准), metric, direction, camera_side | 初始化 |
| `rule_versions` | 一版动作规则 | exercise_code, version, params_json, rationale, author, **reviewer**, is_active | 康复师/算法 |
| `plans` | 一份训练计划 | title, start/end_date, days_per_week, status, goal_text | 康复师 |
| `plan_items` | 计划里的一项 | exercise_code, sets, reps, target_angle, min_valid_angle, rest_sec, rule_version_id | 康复师 |
| `sessions` | 一次训练 | started_at, ended_at, status, camera_side, rule_versions_json（快照）, pain_score, **import_source_key**, **started_at_source** | 患者端 / 离线导入 |
| `session_items` | 一组的结果 | reps_done, reps_valid, peak_angle_max/mean, quality_score, score_breakdown_json, compensation_count, capture_quality, low_confidence, angle_trace_json, **checks_json**, **measurement_angle_json**, **calibration_json**, **needs_review** | 患者端 / 离线导入 |
| `reps` | 一次动作 | rep_index, peak_angle, duration_ms, valid, flags_json, **hold_s**, **return_s**, **bridged_gaps**, **needs_review** | 患者端 / 离线导入 |
| `session_events` | 一条逐时刻提示事件（20260919 新增） | session_item_id, rep_index（可空）, timestamp_s, code, message, severity, raw_json | 离线导入（原型 feedback_events 原样存，不用于评分） |
| `alerts` | 一条提醒 | type, severity, message, acknowledged_by/at | 服务端自动 / 离线导入（仅 low_capture） |
| `audit_logs` | 一次敏感操作 | user_id, action, target, detail_json, ip | 服务端自动 |

## 提醒类型（`alerts.type`）

| type | 触发 | 级别 |
|---|---|---|
| `pain_high` | 训练后疼痛自评 ≥ 6 | high |
| `compensation_high` | 某组代偿次数 / 完成次数 ≥ 30% | warn |
| `angle_drop` | 峰值角度比近 3 次均值退步 ≥ 8° | warn |
| `inactive_3d` | 有激活计划但 ≥ 3 天没训练（康复师打开列表时检查） | warn |
| `low_capture` | 某组拍摄质量 < 60% | info |

阈值是 v0.1 假设值，等康复需求与医学沟通（陈）审核后改；改在 `backend/main.py` 的 `generate_alerts()`，下一版挪进规则表。

## 训练记录离线导入（20260919 新增，`database/import_results.py`）

背景：姿态识别原型（`algorithm/rehab-pose-demo`，v0.6）现在没有 API/WebSocket，产出的是本地
`results/<目录>/` 里的 `summary.json` + `frames.jsonl`（+ 可选 `assessment.json`）。这套原型是
另一个人独立设计的状态机，字段名字和这份数据字典原本假设的（`start_threshold`/`hold_ms` 那套）
大量对不上，详细映射依据见 `知识库/10_卡片/项目/康迹-原型输出落库映射-20260918.md`。
`database/import_results.py` 是离线批量导入这些结果目录的脚本，用法见脚本顶部的 docstring。
下面这些新增列都直接写在 `database/schema.sql` 对应表的 `CREATE TABLE IF NOT EXISTS` 语句
末尾（新建库自动有）；已经在跑的旧库要补这几列，手工执行一次
`database/migrations/20260919-import-prep.sql`（为什么不能用 `ALTER TABLE` 留在 schema.sql
里自动跑，见 `database/README.md`）。

**动作代号映射**（已拍板，不是这次新猜的）：原型数字代号 1/2/6/8 分别对应
`SEATED_KNEE_EXTENSION`（新增）/`SLR`/`SQUAT`/`STS`；`KNEE_FLEX` 保留，不用于坐姿伸膝。

**新增列的含义**：

- `sessions.import_source_key`：离线导入的幂等去重键，通常是 `summary.json` 的 `created_utc`；
  非导入产生的 session（患者端实时上报）这一列是空的。重复导入同一个结果目录会被脚本直接跳过。
- `sessions.started_at_source`：`started_at` 这个时间戳的可信度标记。
  `observed_wallclock_estimate` = 实时摄像头场景（`timing_source=monotonic_clock`），用
  `created_utc` 减最后一帧时间戳近似算出；`file_write_time_video_replay` = 回放已录制视频文件场景
  （`timing_source=video_presentation_timestamps`），这种情况下帧内时间戳和真实墙钟时间无关，
  `started_at` 只能退化成结果文件写入时刻，**不代表真实训练开始时刻**；`unknown_timing_source`
  = 样例数据缺这个字段时的兜底。
- `session_items.checks_json`：原型 `assessment.json` 的逐项 `met`/`not_met`/`unable_to_assess`
  判定，按原型 `repetitions[].index`（全局序号，不是组内序号）建 key，如
  `{"3": [{"metric":"amplitude","status":"met",...}]}`。`assessment.json` 缺失时这一列是空的，
  不阻塞导入（`summary.json`+`frames.jsonl` 已经够算出其余全部字段）。
- `session_items.measurement_angle_json`：二维测量角度参考值（组内可信观测帧的
  `knee_included_deg` 范围），只用来核对，**不与 `peak_angle_max` 的口径混用**——原型动作
  `SLR`/`SQUAT` 的 `peak_angle_max`/`reps.peak_angle` 存的是"相对初始方向的变化量"（已扣掉
  90 度人工偏移），不是解剖角，`SEATED_KNEE_EXTENSION`/`STS` 才是真实髋-膝-踝夹角。
- `session_items.calibration_json`：原型标定基线（`measures.py` 的 `baseline`，含
  `captured_at_s`）原样保留，供核对相对角度换算依据。
- `session_items.needs_review` / `reps.needs_review`：原型 `bridged_gaps>0`（用了短暂预测补帧）
  时为 1，提示这条数据不完全是直接观测，谨慎作为强提醒或趋势依据。
- `reps.hold_s` / `reps.return_s` / `reps.bridged_gaps`：原型 `target_hold_s`/`return_s`/
  `bridged_gaps` 原样存，用来做"保持时间退步"这类趋势提醒（比塞进 `flags_json` 字符串更适合）。

**评分口径（20260919 更新，常明确要求）**：原型不产出 0-100 分，也**不能**按提示事件条数反推一
个分数——提示有冷却时间（同一秒钟前倾了几次也只算一次提示），识别不到（低置信度、遮挡）不等于
动作做对了，"保持不足"/"无法判断"这类状态到底该怎么处理，还没和 陈（临床）共同定下来。所以
`import_results.py` 默认（不传 `--score-mode`）**不写** `quality_score`（留 NULL），
`score_breakdown_json` 只存各维度的原始输入，不折算成分：

```json
{"reps_valid": 9, "reps_target": 10, "reps_done": 10, "amplitude_ratio": 0.87,
 "compensation_event_count": 2, "too_fast_event_count": 0, "capture_quality": 0.93,
 "provisional": true, "reason": "评分口径待常/陈确认：..."}
```

只有显式传 `--score-mode contract-d` 才会按 `docs/03-接口契约.md` D 节公式现算并写进
`quality_score`，这时 `score_breakdown_json` 是各维度加权后的分数（点数，和之前一样），并多一个
`"score_mode":"contract-d"` 标记，仅供联调对比用，不代表这个公式已经拍板。`rest_angle`/
`target_angle` 对 `SEATED_KNEE_EXTENSION`/`STS` 直接用原型 `effective_parameters.rest_max_deg`/
`target_deg`（真实角度）；对 `SLR`/`SQUAT` 用 0 和 `effective_parameters.target_deg - 90`（换算
回相对量的目标值，因为这两个动作的 `target_deg` 在原型里本来就是"90+相对目标量"）。这套换算是
数据库（得）自己的推导，不是常/陈明确拍板的，需要确认，见对应 PR 的「待确认」。

`session_items.compensation_count` 这一列名字不变（改列名成本高，schema.sql 里已经把注释改成
「提示事件计数，非代偿次数」），含义澄清：它是非 `too_fast` 类提示事件的触发次数，不是"确诊代偿
次数"，不代表严重程度，离线导入默认不拿它反推评分。

**逐条提示事件（`session_events` 表，20260919 新增）**：原型的 `feedback_events`（每一条"身体
前倾""速度过快"这类实时提示，含 `timestamp_s`/`code`/`message`/`level`）不能被 `alerts` 表代替——
`alerts` 是给康复师看的汇总提醒（一条 session 一类问题一条），`session_events` 是逐时刻纠错记录，
一条事件一行，`import_results.py` 把 `summary.feedback_events` **原样逐条**写进来，`raw_json`
存整条原始事件兜底。事件自带动作序号（原型部分事件有 `rep_index`）时，直接归那一次动作所在的组；
没带就按时间戳分配给对应的 `session_items`（哪个 `training_set` 的时间窗覆盖这个时间戳），组间空档
（如休息期间）的事件就近分给外包络边界更近的那组。`rep_index` 同样优先用事件自带的序号（原型是全局
动作序号，落库换算成组内序号，和 `reps.rep_index` 对齐），没带才按时间戳落在哪个 rep 的
`[start_s,end_s]` 窗口内回填，两样都判不出时为空。这里不能只按时间窗判：
`AMPLITUDE_BELOW_TARGET`/`HOLD_TOO_SHORT`/`RETURN_TOO_FAST` 这三类"这一次没达标"的提示，原型是在该
次动作被判定完成的那一帧才发出的，时间戳必然晚于这次 rep 的 `end_s`（`end_s` 取的是回到静息位的时
刻），只按时间窗回填会让最该有 `rep_index` 的三类事件全部落空。这张表只是原样保留原始提示记录，
供以后回放或做别的判定逻辑用，**不用于计算 `quality_score`**。

**新版 `rule_versions`**：`SEATED_KNEE_EXTENSION`/`SLR`/`SQUAT`/`STS` 各新增一版
`v0.6-proto`，`params_json` 是原型 `config/knee_extension.json` 的真实键名和数值（不是种子
数据那套阈值体系，两套状态机设计不同，不能互相覆盖），`is_active=0`，未经 常/陈 确认前不影响
现有 `plan_items` 默认使用的 `v0.1`。

## 隐私相关字段说明

- `angle_trace_json`：每 100 ms 一个角度数字（如 `[168,150,120,...]`），**不是**关键点坐标，反推不出画面。可通过环境变量关掉（下一版）。
- `device`：只存 UA 前 200 字符，用于排查兼容问题。
- 用户权利：导出 = `GET /patients/{id}/export.csv`；删除 = 下一版加 `DELETE /patients/{id}`（级联删 sessions/items/reps，审计留痕）。

## 迁移 PostgreSQL 时要改的

- `AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`
- `datetime('now','localtime')` → `now()`
- `substr(started_at,1,10)` → `started_at::date`
- 其余不动。

### 视觉报告增量表（待数据库负责人审核）

backend/migrations/002_training_reports.sql 的 training_reports 每行保存一次视觉训练结束结果。字段：id、patient_id、client_id（与patient_id联合唯一）、exercise_id（seated/supine/squat/stand）、result_json（真实简报、逐次指标、提示、计划）、created_at、read_by、read_at。按当前患者康复师关联授权，不存视频或原始关键点，不进入既有趋势或保底评分。

### 报告录像增量表（003，待得审核）

上述不存视频约束已由用户本次录像需求扩展。report_videos 以 report_id 关联 training_reports，保存 mime、size、sha256、duration_s、preview_flipped、chunk_count、state、created_at。report_video_chunks 以 (report_id, chunk_index) 为主键，data 为实际录像 BLOB。state=uploading 不可播放；完整校验后为 ready。录像不参与动作评分，原始关键点仍不存储。

### 视觉方案增量表（004，待得审核）

visual_prescriptions：id、patient_id、therapist_id、status(draft/published)、body_json、created_at。发布版不可变，读取患者当前关联康复师的最新发布版；发布清理该作者的旧草稿。body_json 保存动作目标、组次、患侧、频次、周期、疼痛自报提醒及文字建议，字段见契约H。沿用独立视觉动作代号，不强行映射旧种子表。

### 患者自主选择增量表（005，待得审核）

patient_training_selection：patient_id（主键）、condition（目前仅 knee_osteoarthritis，可空）、exercise_ids_json、updated_at。首次注册无记录；显式清空保留 null 与空列表。仅为自主选择，不更新诊断或康复师处方，接口见契约 J。
