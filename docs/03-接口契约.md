# 03 · 接口契约（算法 → 前端 → 后端）

## J. 患者自主选择（待景、得审核）

GET /api/v1/me/training-selection 返回 {selection:null|{condition,exercise_ids,updated_at}}。PUT 同路径接受 {condition:null|knee_osteoarthritis,exercise_ids:[seated|supine|squat|stand]}，空数组配null清空，非空必须选择唯一支持方向，动作不能重复。仅患者本人，ID由登录身份确定，不接受指定其他患者。自主选择不代表诊断，不修改 visual_prescriptions，康复师发布版始终优先。新账号默认null，不注入默认动作；演示账号的初始展示由前端明确标识。

## H. 实时视觉方案（新增，待审核）

GET /api/v1/patients/{pid}/visual-prescription：关联康复师读取自己的最新草稿和发布版。POST 同路径：{status: draft|published, title, side: left|right, phase, days_per_week, notes, items:[{exercise_id: seated|supine|squat|stand, sets, reps, target_deg, hold_s, return_s, rest_s}]}。返回 {id,...}。发布为新增不可变版本，不覆盖历史；草稿不影响患者。GET /api/v1/me/visual-prescription 返回 {prescription: 当前关联康复师最新发布版或null}。

target_deg 对动作1/8是膝夹角，对2/6是相对标定起始位的抬腿/屈膝幅度，不能混成解剖角。hold_s 为连续保持下限，return_s 为返回用时下限，rest_s 为组间休息。完整范围以 backend/plan_parameters.py 为准。每次开始训练向本机视觉 /api/live/start 传 targets:{target_deg,hold_s,return_s,rest_s}；视觉引擎冻结生效值，报告携带方案版本与本次实际组次快照。患者已打开页面每15秒空闲刷新；训练中不热改。

## 总览：数据在三方之间怎么流

### 账号注册（新增，待三方审核）

`POST /api/v1/auth/register`，无需令牌。请求：`{username, password, display_name, role: "patient"}`。
username 为手机号或邮箱（去首尾空格、邮箱转小写），display_name 为 1–50 字显示名，password 为 5–15 字符且同时含英文字母和数字。
成功返回 HTTP 201：`{ok: true, username, role: "patient"}`，随后使用 `/auth/login` 登录。
错误返回 `{error: "中文原因"}`：400 参数错误，409 账号重复；模型校验失败 422 为 FastAPI 的 detail 数组。
注册事务创建独立机构隔离空间、患者账号、空患者档案和 register 审计记录。不自动加入演示机构、不生成治疗方案或知情同意记录。
康复师账号暂不开放自行注册，仍由团队配置；患者与机构绑定流程待团队确定。手机号/邮箱目前仅为登录名，未验证号码或邮箱所有权。
前端必须等待服务端注册成功，不在 localStorage 保存账号密码；登录成功后的业务数据加载失败不应删除有效登录令牌。

```
摄像头帧 ──▶ [后端与视觉算法（常）·算法模块] ──帧级指标──▶ [前端（景）] ──组级结果──▶ [后端与视觉算法（常）·API] ──▶ 数据库
                    ▲                          │                       │
              规则参数（阈值）◀────────────────┴───────────────────────┘
```

- **算法模块只吃关键点，只吐指标**：不碰摄像头、不碰网络。
- **前端只吃指标，只画界面和攒一组的结果**：不自己算角度。
- **后端 API 只吃组级结果**：不收视频、不收关键点，规则参数由后端下发。

## A. 帧级契约（算法 → 前端）

### 账号关联接口（新增，待审核）

以下接口均要求 Bearer 登录令牌，角色为 patient 或 therapist。

- `POST /api/v1/care/search`：`{account}` 精确匹配对方的注册手机号、邮箱或用户名，返回 `{users:[{id,display_name,role}]}`。不返回档案、其他联系方式或患者列表；邮箱转小写。
- `GET /api/v1/care/connections`：`{connections,requests}`，只返回本人的已关联对象与待处理申请。
- `POST /api/v1/care/requests`：`{user_id}` 发起申请，201 返回 `{id,status:"pending"}`。
- `POST /api/v1/care/requests/{id}/respond`：`{action:"accept"|"reject"|"cancel"}`。仅接收方可以接受/拒绝，仅发送方可以撤回。
- `DELETE /api/v1/care/connections/{patient_id}`：双方均可解除，暂停患者的 active 计划，保留历史记录。

患者暂限一位主责康复师；康复师可关联多位患者。接受时事务写入已有 patients.therapist_id，不转移机构归属；同时取消该患者其余待处理申请。同机构的其他普通康复师不因此获得权限。康复师的列表、详情、计划、趋势、导出、提醒和统计均按 therapist_id 限定；admin 保留原机构边界。新请求、决定与解除均写审计。

邮箱注册账号目前没有手机号；输入注册邮箱即可查找。未实现补绑或联系方式所有权验证。康复师仍由团队配置，搜索与申请不能创建康复师角色。
增量表 care_requests 由 backend/migrations/001_care_requests.sql 初始化，需数据库负责人审核；不修改原14表结构或演示种子数据。

每一帧调用一次，输入关键点，输出：

```json
{
  "value": 96.4,            // 本动作的主指标（度）。候选动作里 KNEE_FLEX/SQUAT/STS = 膝角(180=伸直)，SLR = 髋屈曲角(0=平躺)，以康复师确认结果为准
  "aux": {                  // 辅助指标，给代偿判断用
    "kneeAngle": 96.4,
    "hipAngle": 148.2,
    "trunkLean": 7.5        // 躯干与竖直方向夹角（度）
  },
  "visible": true,          // 四个关键点可见度都 ≥ 规则 min_visibility 才为 true；false 时前端不计数、提示调整
  "confidence": 0.91        // 可选：本帧综合置信度 0-1
}
```

**参考实现**：本地参考前端页面里的 `computeMetrics()`。算法负责人替换它即可，签名不变：
`computeMetrics(landmarks, exercise, side, minVisibility) -> {value, aux, visible, confidence}`（`confidence` 可选）。

### 计数状态机（算法负责，前端调用）

```
rest ──(value 越过 start_threshold)──▶ moving ──(峰值稳定 hold_ms)──▶ peak ──(回到 start_threshold-3°)──▶ rest（记一次）
```

每记一次，产出一条 **rep**：

```json
{ "rep_index": 3, "peak_angle": 95.2, "duration_ms": 3800, "valid": true, "flags": [] }
```

`flags` 枚举（只能用这些，前端靠它显示提示、后端靠它扣分）：

| flag | 含义 | 触发条件（规则参数） |
|---|---|---|
| `amplitude_low` | 幅度不够 | 峰值没达到 `min_valid_angle` |
| `too_fast` | 过快 | 单次时长 < `min_rep_ms` |
| `trunk_lean` | 躯干前倾/侧倾 | `aux.trunkLean` > `trunk_lean_max_deg` |
| `knee_bent` | 膝没伸直（直腿抬高专用，候选动作） | `aux.kneeAngle` < `knee_straight_min_deg` |
| `hip_shift` | 髋部明显移动（屈膝专用，候选动作） | 预留 |
| `arm_assist` | 借助手臂（坐站专用，候选动作） | 预留 |

`valid` = 达到有效幅度 **且** 没有 `too_fast`。代偿类 flag（trunk_lean / knee_bent / hip_shift / arm_assist）不影响 valid，但计入 `compensation_count`。

## B. 组级契约（前端 → 后端）：`POST /api/v1/sessions/{id}/items`

一组做完上传一条。**这是整个系统最重要的一个接口。**

```json
{
  "plan_item_id": 12,           // 对应计划里的哪一项（自由训练可为 null）
  "exercise_code": "KNEE_FLEX", // 候选：SLR / KNEE_FLEX / SQUAT / STS，以康复师确认结果为准
  "set_index": 1,
  "reps_target": 10,
  "reps_done": 10,              // 状态机数出来的
  "reps_valid": 9,              // valid=true 的个数
  "peak_angle_max": 97.5,       // 本组"最好的一次"峰值（down 类动作取最小角，up 类取最大角）
  "peak_angle_mean": 93.2,
  "duration_ms": 41000,
  "quality_score": 78.5,        // 可选。不传则后端用 scoring.py 按激活规则算
  "score_breakdown": {"completion": 27, "amplitude": 20, "posture": 18, "tempo": 8, "stability": 5.5},
  "compensation_count": 1,
  "capture_quality": 0.93,      // 可见帧 / 总帧
  "low_confidence": false,      // capture_quality < 0.6 时为 true；后端把这组排除出趋势、不生成强提醒
  "angle_trace": [168, 150, 120, 98],   // 可选：每 100ms 一个点的主指标，画曲线用；不是关键点
  "reps": [ {"rep_index": 1, "peak_angle": 95.2, "duration_ms": 3800, "valid": true, "flags": []} ]  // A 节的 rep 数组
}
```

返回：

```json
{ "item_id": 88, "quality_score": 78.5, "score_breakdown": {}, "rule_version": "v0.1" }
```

## C. 规则参数（后端 → 算法/前端）：`GET /api/v1/me/plan/today` 里每项自带 `rule.params`

以 `KNEE_FLEX v0.1`（database/seed/seed.json 里的种子数据）为例：

```json
{
  "metric": "knee_angle", "direction": "down",
  "rest_angle": 170, "start_threshold": 155, "target_angle": 100, "min_valid_angle": 120,
  "hold_ms": 500, "min_rep_ms": 1500, "max_rep_ms": 10000,
  "hip_shift_max": 0.1,
  "smoothing_window": 5, "min_visibility": 0.6,
  "score_weights": {"completion": 0.30, "amplitude": 0.25, "posture": 0.25, "tempo": 0.10, "stability": 0.10}
}
```

- `direction`：`down` = 峰值时角度变小（屈膝、深蹲），`up` = 角度变大（直腿抬高、坐站）。状态机用它决定"越过阈值"的方向。
- 计划项上的 `target_angle` / `min_valid_angle` 若不为空，**覆盖**规则默认值（个体化）。
- 参数由康复需求与医学沟通（陈）+ 后端与视觉算法（常）定内容、康复师在规则库页面改；**代码里不许写死任何阈值**。
- 不同动作可用的参数不完全一样，例如 `trunk_lean_max_deg`（深蹲专用）、`knee_straight_min_deg`（直腿抬高专用），全部可选参数见下表：

| 参数 | 适用动作 | 含义 |
|---|---|---|
| `trunk_lean_max_deg` | SQUAT（深蹲） | 躯干前倾角上限 |
| `knee_straight_min_deg` | SLR（直腿抬高） | 膝伸直角下限 |
| `hip_shift_max` | KNEE_FLEX（屈膝训练） | 髋部横移上限 |

## D. 评分（同一公式，前端先算、后端存、后端能复算）

```
总分 = 100 × Σ 权重 × 维度得分(0-1)
完成度 = reps_valid / reps_target
幅度   = |peak_angle_max − rest_angle| / |target_angle − rest_angle|
姿态   = 1 − compensation_count / reps_done
节奏   = 1 − too_fast 次数 / reps_done
稳定   = capture_quality
```

初始权重建议：完成度 30%、幅度 25%、姿态 25%、节奏 10%、稳定 10%（来自商业计划书评分建议，阈值与权重均为初始假设，须由康复专业人员审核）。

参考实现：`backend/scoring.py`（服务端）与参考前端训练页面的 `score()`（客户端），两边必须一致，改一处改两处。

## F. 视觉训练简报同步（新增，待前端与数据库审核）

训练结束后前端上传真实视觉结果的展示快照，患者反馈与已关联康复师读取同一份记录。该流程保留动作1/2/6/8口径，不套用旧种子评分，不替代 B 节 sessions/items 上报。

- `POST /api/v1/training-reports`，患者令牌，请求 `{client_id, exercise_id, result}`。client_id 使用该次视觉会话ID，exercise_id 为 seated/supine/squat/stand。result 只含 brief_report、repetitions、feedback_events、training_session。大小上限2MB，禁止视频和原始关键点。重复提交相同内容返回原记录，内容不同时409。
- `GET /api/v1/training-reports?limit=50`，患者读自己的报告，康复师读当前关联患者报告，最多100条。列表含 id、patient_name、exercise_id、created_at、brief_report、delivery、read_at。仅机构管理员按机构访问。
- `GET /api/v1/training-reports/{id}`，返回完整展示快照和元数据。权限按当前关联重新核验。
- `POST /api/v1/training-reports/{id}/read`，仅当前关联康复师记录已查看。服务端写 read_by/read_at。

患者ID、接收方由登录身份和 patients.therapist_id 确定，前端不能指定。无关联时保存成功但明确显示“尚未关联康复师”，后续接受关联即可查看已有报告。解绑立即失去权限，更换康复师后新康复师可查看历史报告。保存成功仅表示康复师端可查看，不表示已阅读；前端提供保存失败重试与未读状态，下载为可选备份。

增量表由 backend/migrations/002_training_reports.sql 创建，保留原14表及算法判断不变。JSON展示快照不参与旧趋势/评分。无真实测量不能补造正常数据。本次不保存视频、不发送短信或邮箱通知。临床标准仍待康复师确认。

## G. 报告录像（用户新增要求，待前端/数据库审核）

本节替代F节“不保存视频”的旧范围：新训练默认录制无声摄像头原始画面，结束后上传，界面开始前明确提示。JSON报告仍不接收二进制或原始关键点。录像通过专用接口分块保存进SQLite BLOB，元数据和报告一一关联，不公开文件URL。旧报告没有录像，不补造。

- 报告列表新增可选patient_id，须先核验患者权限，再筛选。报告新增video，未上传为null，否则含state、mime、size、chunk_count、duration_s、preview_flipped。
- POST /training-reports/{id}/video，患者本人，{mime,size,sha256,duration_s,preview_flipped}初始化，返回固定chunk_size=1048576及元数据。限制256MiB，webm/mp4；同内容幂等，不覆盖其他录像。
- PUT /training-reports/{id}/video/chunks/{index}，application/octet-stream，每块最多1MiB，核对索引与期望长度；相同块可重试。
- POST /training-reports/{id}/video/complete，确认块齐、文件头和SHA256后标ready。缺块、不同内容409。
- GET /training-reports/{id}/video，元数据；GET /training-reports/{id}/video/chunks/{index}，仅ready返回二进制。逐次鉴权，患者本人或当前关联康复师/机构管理员可读。浏览器带令牌获取分块后组装Blob本地播放，不将令牌放视频URL。

新增003_report_videos.sql创建report_videos、report_video_chunks，原表不变。上传失败明确显示重试，不当作已保存。临时录像存浏览器IndexedDB供刷新后重试，上传完成删除本地暂存。网页单次录像达到约240MiB会结束训练，避免无限缓存；不同浏览器录制能力需验证。

H 节补充：方案另保存 daily_sessions（每日1–10次）、duration_weeks（1–52周）、pain_pause_score（0–10），随患者方案说明展示。疼痛阈值是自报不适提醒，不是视觉自动检测或自动停机。默认分别为1、2、5，频次为展示性计划，不实现日历排程。

- POST /api/live/start：exercise 为1/2/6/8，side 为 left/right，facing 默认 auto，sets/reps 为目标组次，backend 默认 rtmpose，targets 为已发布方案参数。动作2/8/6必须分别携带 rule_version：slr_v0.1_surface、sts_v0.1_dual_baseline、squat_v0.1_joint。返回 session_id、model、stores_video:false。
- POST /api/live/{id}/frame：image/jpeg 请求体及 X-Capture-Time 秒时间戳，或 JSON {image:Base64图像,timestamp_s:秒}。返回 value/aux/visible/confidence、keypoints、frame_size、measurement_metrics、feedback_events、calibration、training_progress、new_reps、guidance。角度为二维估计；缺失值不当作0或合格。
- POST /api/live/{id}/subject：训练者选择；surface、sts-calibration、squat-setup 为对应动作标定入口，结构以各分析器校验及前端调用为准。需一起更新网页与服务，不保证跨旧版本标定兼容。
- POST /api/live/{id}/stop：结束并释放临时会话，返回真实简报、逐次记录和事件。前端再按 F/G 节保存报告和录像；视觉服务本身不保存录像。会话不存在返回404，参数无效400。

本地摄像头可在 localhost/127.0.0.1 安全上下文使用。公网版本必须另做HTTPS、认证、资源限制及服务地址配置；本次源码归档未实现公网部署。
