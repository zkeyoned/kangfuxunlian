# 0002 · 姿态识别原型（v0.6）训练记录离线导入

- 日期：2026-09-19
- 背景：`algorithm/rehab-pose-demo`（PR #1 `backend/import-pose-demo-v0.6`，2026-09-19 已合并进 main）现在没有 API/WebSocket，
  产出的是本地 `results/<目录>/` 下的 `summary.json`+`frames.jsonl`（+可选 `assessment.json`）。这套原型是
  另起的一套状态机设计，字段名字和 `database/schema.sql`/`docs/03-接口契约.md` 原本假设的（`start_threshold`/
  `hold_ms` 那套）大量对不上。详细映射依据见 `知识库/10_卡片/项目/康迹-原型输出落库映射-20260918.md`。为了
  在比赛前尽快让数据库真正被用起来（能画趋势图、出报表演示），先做离线批量导入（方案 a），不等原型封装成
  网络接口（方案 b）。
- 决定：
  1. 新增 `database/import_results.py`：读一个结果目录，算出 `docs/03` D 节的评分，写进
     `sessions`/`session_items`/`reps`（必要时 `alerts`），按结果目录名/`created_utc` 幂等去重。
  2. 动作代号映射：原型数字代号 1/2/6/8 分别对应 `exercises.code` 的
     `SEATED_KNEE_EXTENSION`（新增）/`SLR`/`SQUAT`/`STS`；`KNEE_FLEX` 保留但不用于坐姿伸膝。
  3. `schema.sql` 各对应表的 `CREATE TABLE IF NOT EXISTS` 语句末尾追加列，不改动、不重排已有列：
     `sessions.import_source_key`/`started_at_source`；`session_items.checks_json`/
     `measurement_angle_json`/`calibration_json`/`needs_review`；`reps.hold_s`/`return_s`/
     `bridged_gaps`/`needs_review`。含义见 `docs/02-数据字典.md`「训练记录离线导入」一节。
     没有用 `ALTER TABLE` 留在 `schema.sql` 里：`backend/db.py` 的 `init_db()` 每次启动都会对
     已有库重跑一遍 `schema.sql`，`ALTER TABLE ADD COLUMN` 不支持 `IF NOT EXISTS`，会在已经跑过
     一次的库上报 `duplicate column name`。已有旧库要补这几列，改用
     `database/migrations/20260919-import-prep.sql` 手工执行一次，新建库不用管这个文件。
  4. `SLR`/`SQUAT` 两个动作的 `peak_angle_max`/`reps.peak_angle` 存的是"相对初始方向的变化量"（原型已扣
     掉 90 度人工偏移），不是解剖角，和 `SEATED_KNEE_EXTENSION`/`STS` 存的真实髋-膝-踝夹角不是同一个量纲，
     不能在图表上直接比较。
  5. `exercises`/`rule_versions` 各新增一版 `v0.6-proto`（`is_active=0`），`params_json` 是原型
     `config/knee_extension.json` 的真实键名和数值，不覆盖现有 `v0.1`。
- 影响谁：后端与视觉算法（常）——以后把原型封装成 API 时，这套换算规则（角度口径、评分公式、事件-时间窗
  归属）可以原封不动搬进后端的请求序列化器；康复需求与医学沟通（陈）——需要确认动作代号映射、`SLR`/`SQUAT`
  阈值的临床意义；前端（景）——趋势图如果要同时展示 `SLR`/`SQUAT` 的历史数据，需要知道这两个动作存的是相对
  量不是绝对角度。
- 待确认（不是这条决策记录能拍板的，列在这里等常/陈过目）：
  1. 动作代号 1/2/6/8 ↔ `SLR`/`SQUAT`/`STS`/`SEATED_KNEE_EXTENSION` 的映射本身（`常` 已在会话里口头拍板，
     这里落成文字记录，仍需要书面确认一次）。
  2. `import_results.py` 里 `SLR`/`SQUAT` 的评分用 `rest_angle=0`、`target_angle=effective_parameters.
     target_deg-90` 这个换算，是数据库（得）自己的推导，不是明确给的公式，需要确认。
  3. `v0.6-proto` 版本的 `score_weights`（完成度30%/幅度25%/姿态25%/节奏10%/稳定10%）是照抄 `v0.1` 的
     初始假设值，原型不产出权重，需要康复专业人员审核。
  4. 事件代号 `SLR_TOO_HIGH`（抬腿幅度过大）、`SQUAT_TOO_DEEP`（下蹲过深）在契约 A 节的六个 `flags` 枚举里
     没有对应语义，目前不落进 `flags_json`，只计入代偿次数之外，需要决定要不要扩展枚举。
  5. `session.status` 的取值映射（`stopped_by_user`/`time_limit`→`aborted`，`plan_completed`/`completed`→
     `finished`，`failed` 直接跳过不落库）是按字面猜的，需要确认。
  6. 回放视频文件（`timing_source=video_presentation_timestamps`）场景下 `sessions.started_at` 只能退化成
     结果文件写入时刻，已打 `started_at_source` 标记，但如果以后真的有这个场景，需要产品/前端决定怎么向
     康复师解释这个时间戳的含义。
- 按队友反馈补充（2026-09-19，后端与视觉算法（常）提出，本条记录随之修订）：
  1. **逐时刻纠错记录必须存下来**。常指出 `alerts` 是给康复师看的汇总提醒，替代不了原型
     `summary.feedback_events` 那种一条一条的实时提示。处理：新增 `session_events` 表
     （`session_item_id` 外键 `ON DELETE CASCADE`、`rep_index` 可空、`timestamp_s`、`code`、
     `message`、`severity`、`raw_json`），写在 `CREATE TABLE IF NOT EXISTS` 里跟着 `init_db()`
     自动建；`import_results.py` 把 `feedback_events` **原样逐条**落库，`raw_json` 存整条原始
     事件兜底。事件先归属到对应的 `session_items`（自带动作序号的按序号，没带的按时间戳落在哪
     一组的时间窗），`rep_index` 优先用事件自带的序号换算成组内序号，没带才按 rep 的
     `[start_s,end_s]` 时间窗回填。这里踩过一个坑：`AMPLITUDE_BELOW_TARGET`/`HOLD_TOO_SHORT`/
     `RETURN_TOO_FAST` 是在这一次动作判定完成的那一帧才发出的，时间戳必然晚于该次 rep 的
     `end_s`，只按时间窗回填会让最该有 `rep_index` 的三类事件全部落空。
  2. **评分不能按提示条数扣分**。常指出：提示有冷却时间（同一秒前倾好几次也只发一条），识别不到
     （低置信度、遮挡）不等于动作做对了，"保持不足"/"无法判断"这类状态该怎么处理还要和 陈（临床）
     共同定。处理：`import_results.py` 默认**不写** `quality_score`（留 NULL），
     `score_breakdown_json` 只存各维度的原始输入（`reps_valid`/`reps_target`/`reps_done`/
     `amplitude_ratio`/`compensation_event_count`/`too_fast_event_count`/`capture_quality`）并标
     `"provisional": true` 和 `reason`；只有显式传 `--score-mode contract-d` 才按 `docs/03` D 节
     公式现算并写进 `quality_score`（`score_breakdown_json` 多一个 `"score_mode":"contract-d"`
     标记），仅供联调对比，不代表这个公式已经拍板。两种模式都有测试覆盖。
     `session_items.compensation_count` 的语义同时澄清为"提示事件数"（非 `too_fast` 类提示的触发
     次数），不是"确诊代偿次数"，列名不改（改列名成本高），注释和 `docs/02` 已写明。
     原「待确认」第 2、3 条（`SLR`/`SQUAT` 的角度换算、`score_weights` 照抄 `v0.1`）因此降级：
     现在默认根本不算分，这两条只在 `--score-mode contract-d` 下才生效，仍然待确认。
  3. **`docs/01-技术方案.md` 与原型架构不一致**。`docs/01` 第 46 行写的是"端侧优先：在浏览器里跑
     MediaPipe WASM"，而现在的原型是跑在本机的 Python 服务。这不是数据库目录能改的文件，已按根
     `AGENTS.md`「不确定时怎么办」的要求，在 `PROGRESS.md` 末尾「待讨论」段落记一条，建议由后端
     负责人更新 `docs/01` 与 `docs/04-部署方案.md`。
- 按审查意见修正（第四次提交，2026-09-19，后端与视觉算法（常）审 PR 提出）：
  1. **`compensation_count` 的文档说法和代码对不上**。PR 说明写的是"非速度类提示事件数量"，
     代码实际是"每次动作内去重后的提示类型数"（同一次动作里前倾提示两次，`session_events`
     两条，计数只记 1）。处理：统一成一种，口径定为
     **每次动作内、非速度类、按提示代号去重的类型数，再按组求和**（比直接数条数更抗冷却时间
     和重复提示的影响），`database/schema.sql` 列注释、`docs/02-数据字典.md`、PR 正文三处用
     同一句话。去重只统计能映射到契约 A 节代偿类 `flags` 的代号：
     `AMPLITUDE_BELOW_TARGET`/`HOLD_TOO_SHORT`/`RETURN_TOO_FAST` 是"这一次没达标"的完成判定
     提示，不是代偿，不能算进来；`SLR_TOO_HIGH`/`SQUAT_TOO_DEEP` 仍不计入，见「待确认」第 4 条。
     测试：同一提示在一次动作里出现两次，`compensation_count` 只加 1，`session_events` 仍是两条。
  2. **一次动作都没完成时训练信息整段丢失**。以前按已完成的 `repetitions` 建组，患者尝试多次
     但一次没完成（识别中断、幅度不足、遮挡）时没有 `session_item`，逐条事件也没地方挂。
     处理：即使 0 次完成，也为该 `training_set`（无分组信息时就是整段录制）落一条
     `session_items`：`reps_done=0`、`reps_valid=0`、`low_confidence=1`、`needs_review=1`、
     `quality_score=NULL`（`--score-mode contract-d` 也不给分），`checks_json`（改存中断的尝试
     及其 `interruption_reason`）与 `calibration_json` 照存，所有 `feedback_events` 挂到这条
     item 下面（`rep_index` 为空）；`sessions.status` 用 `aborted`，除非 `summary.status` 明确
     是已完成。测试：构造没有完成动作的 summary，断言 1 条 item、0 条 reps、事件全部入库。
  3. **`capture_quality` 偏高**。以前分母只算已完成动作时间窗内的帧，等于把"根本没拍到人"的
     时间从分母里摘出去。处理：分母改成该组的**整个时间跨度**（从该组首次尝试或标定开始到该组
     结束，标定失败与中断的尝试都进分母；这一组没有任何 rep 时取整段录制）。跨度算法：已完成
     动作的外包络打底，再把 `interrupted_attempts` 和 `calibrations[].captured_at_s` 按就近
     规则补进对应组。旧口径的比值另存进 `session_items.measurement_angle_json` 的
     `capture_quality_completed_reps`（默认模式的 `score_breakdown_json` 里也有一份）供对比。
     测试：前半段可见率低、完成动作窗内可见率高的 frames，新口径明显低于旧口径。
  4. **未知 `summary.status` 不再偏乐观**。以前默认按 `finished` 处理（原型加个新状态、或跑崩了
     只写半个 summary，都会被当成"跑完了"）。处理：默认映射到 `aborted`、打 warning、并把本次
     导入的所有组标 `needs_review=1`；新增 `--strict` 开关，遇到未知状态直接拒绝导入并以非零
     退出码结束，一条都不写。两种情况都有测试覆盖。
- rebase 到 PR #17 之后的适配（2026-09-21，本分支重新基于 main 的 `d4ced96`）：
  1. **`contract_reps` 优先**。PR #17 让原型自己产出契约 A 节要求的扁平 rep
     （`rehab_pose/contract.py` 的 `rep_to_contract`：`rep_index`/`peak_angle`/`duration_ms`/
     `valid`/`flags`），写在 `summary.contract_reps` 里。`import_results.py` 有这一段时就直接

     同时看了 `target_comparison` 和 `feedback_events`，判定比这边全（实测原型自带样例那一次
     动作，本脚本原逻辑判合格，契约折算判 `valid=false`、`flags=["too_fast"]`，以原型为准）。
     没有这一段的老结果目录走原逻辑，行为不变；`score_breakdown_json` 多一个 `rep_source` 键
