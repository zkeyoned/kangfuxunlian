# 公网延迟控制交接（给得）

## 问题与改动

旧网页约10fps采集，16帧待发、每批8帧，网络或推理变慢时不断处理旧画面。此次修改纯前端调度，模型、动作阈值及服务器接口不变。

- 待发最多2帧，每批最多2帧，发出前移除超过0.6秒的旧帧。保留真实采集时间戳。
- 根据请求时长把采集间隔调到100–200ms，不让新队列无限增长。
- 结果采集时间距现在超过1.5秒就不绘制。每250ms检查显示时效；旧图、旧骨架与旧指标清除，露出实时摄像头并提示暂停动作。
- 请求5秒超时，不重试可能已执行的请求。结束训练不继续发送排队画面。
- 跳帧或网络错误在简报注明，次数仅代表已识别部分。原规则时间间隔大于max_gap_s（默认0.3秒）会中断未完成动作，不补算连续保持。

## 发布

本分支叠加在本地性能PR #34上，#34依赖RTMPose对齐PR #33。请先检查已部署分支，合并/拣选时解决版本差异，不要用旧压缩包覆盖主分支。

1. 在测试副本同步该分支的完整frontend，至少包括app.js、frame-queue.js、index.html，以及#34新增的frame-encoder.js、frame-encoder-worker.js。无需改库、重置账号或替换模型。
2. 使用现有部署流程刷新静态资源缓存版本，确认页面app.js和frame-queue.js版本已改变；浏览器Ctrl+F5。
3. 正常网络测试：锁定同一患者，坐姿伸膝、前后倾、保持、多人经过；核对计次及左右腿没有变更。再测试断网、结束按钮。
4. 慢网络测试：开发工具Network增加2秒延迟。页面应在约1.5–1.75秒后显示实时摄像头与“请暂停动作”，旧指标为--，不能继续展示20秒前的动作。恢复网络后重新回到起始姿势。
5. 连续两分钟真实训练，记录开发工具window.__remotePerformance。它仅含最近120次请求耗时、每批帧数、最后一帧processing_ms、待发数和跳帧数，不含视频。最后一帧耗时不是整批耗时，不能直接从请求总时长减它当作纯网络时间。

## 若恢复后仍频繁提示暂停

这次消除的是旧帧积压，不会把慢CPU或慢网络变快，实时视频流畅也不等于识别已恢复。

请检查视觉服务CPU占用、内存/交换、同时训练人数及反向代理请求耗时，并在服务器回环地址用同一输入测推理/批处理耗时，再与公网请求比较。已有RTMPose同模型要求保持不变。若稳定吞吐不足以维持规则允许的采样间隔，应明确暂不支持实时评估；另行优化计算资源/模型运行方式，不能放宽动作阈值掩盖。

公网由得部署，本次没有登录或修改公网服务器。建议先验收再正式发布。

## 已验证

- 队列模拟连续积压50帧，始终只留最新2帧，发送顺序保持；过期、停止、错误不重试覆盖。
- 前端测试覆盖过时结果不覆盖页面、请求无响应时预览恢复、正常结果与画面匹配；原页面回归通过。
- 规则核心12项及隔离临时数据库完整API通过，正式训练记录未改。
